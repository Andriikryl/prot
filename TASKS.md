# Tracker (мини-Linear): план и задачи

Формат работы: задачу делает разработчик, Claude проверяет (код, сборка, запуск) и даёт замечания по пунктам. Готовых решений не даём, только направление и ссылки на доки.

Сдача: напиши «готово 1.х», и я проверю.

Доки Next 16 лежат в `node_modules/next/dist/docs/01-app/`. Читать перед работой: API отличаются от старых версий.

## Стек

Next.js 16.4, React 19.3, Postgres 17 (Docker), Drizzle, Better Auth, zod, Tailwind 4, nuqs, dnd-kit, TanStack Virtual, Vitest, Playwright.

## Сущности

User, Workspace, Project, Issue (статус, приоритет, исполнитель, метки), Comment, ActivityLog.

## Структура маршрутов (цель)

```
app/
  (auth)/login, register
  (app)/
    [workspace]/
      layout.tsx            # сайдбар, проверка членства
      issues/page.tsx       # список + фильтры из URL
      issues/[id]/page.tsx  # полная страница задачи
      @modal/(.)issues/[id] # перехваченная модалка (intercepting + parallel)
      projects/[id]/
      settings/
  api/events/route.ts       # SSE для realtime
```

## Общий план (~5–6 недель)

| Этап | Что делаем | Что осваиваем |
|---|---|---|
| 1. Фундамент (~3–4 дня) | Postgres + Drizzle, схема, миграции, сиды, каркас с сайдбаром | RSC, структура `app/`, запросы к БД в серверных компонентах |
| 2. Auth и доступ (~3 дня) | Регистрация, сессии, workspace, роли, защита маршрутов | proxy, DAL-слой с проверкой прав, `cookies()`, `headers()` |
| 3. Список задач (~4 дня) | Фильтры, сортировка, пагинация через URL, Suspense и скелетоны | Streaming, `loading.tsx`, состояние в URL |
| 4. Мутации (~4 дня) | Создание и правка задач через Server Actions, zod, `useActionState`, `useOptimistic` | Формы, ошибки, ревалидация |
| 5. Продвинутый роутинг (~3 дня) | Модалка задачи по URL | Parallel и intercepting routes, `error.tsx`, `not-found.tsx` |
| 6. Кэширование (~3 дня) | Явная стратегия кэша | Cache Components, теги, `use cache`, PPR |
| 7. Realtime (~4 дня) | SSE, синхронизация с кэшем | Route Handlers, клиентский и серверный стейт, гонки |
| 8. Канбан-доска (~4 дня) | Drag-and-drop, оптимистичные перестановки с откатом | `useTransition`, сложный клиентский стейт, a11y |
| 9. Производительность (~3 дня) | Виртуализация 10k задач, профайлер, React Compiler, CWV | Профилирование, ререндеры, bundle analyzer |
| 10. Качество (~4 дня) | Vitest, Playwright (сценарий с двумя клиентами), CI, Sentry, ADR | Тестирование RSC и actions, наблюдаемость |

## Правила проекта

- Вся работа с БД и проверка прав идёт через один слой `lib/dal`. Компоненты и actions не обращаются к БД напрямую.
- Каждое решение о кэше записываем в `docs/adr/`: что, почему, чем рискуем.
- На каждом этапе сначала делаем «наивно», потом ломаем (гонки, медленная сеть, искусственные задержки) и только потом чиним.

# Этап 1. Фундамент

## Задача 1.1. Postgres в Docker

**Сделать**
- `docker-compose.yml` в корне с сервисом `postgres:17`, именованным volume и healthcheck.
- `.env` (в `.gitignore`) и `.env.example` (в git) с `DATABASE_URL`.
- Скрипты в `package.json`: `db:up`, `db:down`.

**Приёмка**
- [ ] После `npm run db:up` контейнер в статусе `healthy`.
- [ ] После `db:down` и повторного `db:up` данные не пропадают.
- [ ] В репозитории нет паролей, только `.env.example`.

## Задача 1.2. Схема БД на Drizzle

**Сделать**
- Файл `drizzle.config.ts`.
- Схема в `db/schema/`, по файлу на группу таблиц, не один большой файл:
  - `workspaces`, `projects`, `issues`, `comments`, `labels`, `issue_labels` (many-to-many), `workspace_members` (с ролью).
  - У `issues`: `number` (порядковый номер внутри workspace, как `TRK-42`), `title`, `description`, `status` (enum), `priority` (enum), `assigneeId` (nullable), `createdAt`, `updatedAt`.
  - У `workspaces`: `slug` (нужен для маршрутов).
- Таблицы пользователей и сессий Better Auth добавим на этапе 2. Сейчас `assigneeId` и подобные поля оставь обычным `text`/`uuid` без внешнего ключа на пользователей.
- Скрипты `db:generate`, `db:migrate`.

**Приёмка**
- [ ] `npm run db:generate` создаёт SQL-миграцию, `npm run db:migrate` применяет её.
- [ ] Есть внешние ключи с осмысленным `onDelete`: удаление проекта не оставляет задачи-сироты, удаление label не удаляет задачи.
- [ ] Есть индексы под будущие запросы: список задач workspace по статусу, по исполнителю, по дате.
- [ ] `(workspaceId, number)` уникальны.

**Подумать и объяснить:** почему `number` нельзя просто сделать `serial`? (Он должен быть последовательным в рамках каждого workspace.)

## Задача 1.3. Клиент БД и сиды

**Сделать**
- `db/index.ts` с единым экземпляром клиента. В dev Next перезагружает модули, и без защиты будут плодиться соединения (паттерн с `globalThis`).
- Скрипт `db/seed.ts`, запуск через `tsx`: 2 workspace, 3 проекта, ~200 задач с разными статусами и приоритетами, несколько меток и комментариев.
- Скрипт `db:seed` в `package.json`, идемпотентный (повторный запуск не плодит дубли).

**Приёмка**
- [ ] `db:seed` можно запустить дважды подряд без ошибок и дублей.
- [ ] Данные разнообразны (не 200 одинаковых «Task»). Можно без faker.

## Задача 1.4. Каркас приложения

**Прочитать:** `01-getting-started/02-project-structure.md`, `03-layouts-and-pages.md`, `05-server-and-client-components.md`.

**Сделать**
- Структура маршрутов: `app/(app)/[workspace]/layout.tsx` и `issues/page.tsx`.
- `layout.tsx` — серверный компонент: ходит в БД, берёт workspace по slug и список его проектов. Если workspace не найден, показывает `not-found`.
- Сайдбар со списком проектов и ссылками. Активная ссылка подсвечивается (нужен клиентский компонент, держать его максимально маленьким).
- `issues/page.tsx` выводит простой список задач, пока без фильтров.

**Приёмка**
- [ ] Ровно один `"use client"`-компонент в сайдбаре, и можно объяснить, почему он клиентский, а layout нет.
- [ ] Список задач получается прямым запросом в серверном компоненте: без `useEffect` и без API-роута.
- [ ] `/несуществующий-slug/issues` отдаёт 404-страницу.
- [ ] `npm run build` и `npm run lint` проходят без ошибок и предупреждений.
