# Tracker (мини-Linear): план и задачи

Формат работы: задачу делает разработчик, Claude проверяет (код, сборка, запуск) и даёт замечания по пунктам. Готовых решений не даём, только направление и ссылки на доки.

Сдача: напиши «готово 1.х», и я проверю.

Доки Next 16 лежат в `node_modules/next/dist/docs/01-app/`. Читать перед работой: API отличаются от старых версий.

## Стек

Next.js 16.4, React 19.3, Postgres 17 (Docker), Drizzle, Better Auth, zod, Tailwind 4, shadcn/ui (radix-nova, компоненты в `src/shared/ui`), nuqs, dnd-kit, TanStack Virtual, Vitest, Playwright.

## Сущности

User, Workspace, Project, Issue (статус, приоритет, исполнитель, метки), Comment, ActivityLog.

## Структура маршрутов (цель)

```
app/
  (auth)/login, register
  (app)/
    [workspace]/
      layout.tsx            # сайдбар, проверка членства
      issues/page.tsx       # список + фильтры из URL
      issues/[id]/page.tsx  # полная страница задачи
      @modal/(.)issues/[id] # перехваченная модалка (intercepting + parallel)
      projects/[id]/
      settings/
  api/events/route.ts       # SSE для realtime
```

## Архитектура: Feature-Sliced Design поверх Next.js App Router

Решение: фронт строим по FSD (v2.1). Правила ниже сверены с гайдом FSD для Next.js.

### Раскладка папок

```
app/                      # ТОЛЬКО роутинг Next: тонкие page/layout/route, реэкспорты
  (app)/[workspace]/...
  api/.../route.ts
proxy.ts                  # (позже) в корне, рядом с app/
server/                   # БЭКЕНД (алиас @server/*). Не знает про React и UI
  db/                     # схема, миграции, клиент (client.ts), сид; вход для приложения: index.ts (server-only)
  auth/                   # (этап 2) сессии, проверка прав
  <модуль>/               # (issues, workspaces, ...) запросы, мутации, правила доступа
src/                      # ФРОНТЕНД по FSD (алиас @/*)
  _app/                   # FSD-слой app: провайдеры, глобальные стили
  _pages/                 # FSD-слой pages: экраны (UI страницы живёт здесь)
  widgets/                # самодостаточные блоки: sidebar, issue-list, board
  features/               # действия пользователя: create-issue, change-status, filters
  entities/               # бизнес-сущности на фронте: типы, карточки, отображение
  shared/                 # ui-kit (shadcn), утилиты, конфиги
```

Слои FSD `app` и `pages` переименованы в `_app` и `_pages`, иначе Next примет их за свои специальные папки. Бэкенд лежит в корне, в `server/`, и в FSD не входит: в `src/` только фронтенд.

### Правила

1. **Импорты только вниз:** `_app → _pages → widgets → features → entities → shared`. Слайсы одного слоя друг друга не импортируют.
2. **`app/` в корне содержит только реэкспорты**, например `export { IssuesPage as default } from "@/_pages/issues"`. Никакой логики.
3. **«Pages first» (v2.1):** сначала держим код внутри страницы и выносим вниз (в features/entities) только когда появляется второе использование. Не дробить заранее.
4. **Public API:** снаружи слайс импортируется только через его `index.ts`, во внутренности лезть нельзя.
5. **Server/client:** публичный вход каждого модуля `server/*` начинается с `import "server-only"`, поэтому клиентский компонент, который его импортирует, ломает сборку. Исключение: файлы, которые запускаются вне Next (`db/client.ts`, `db/seed.ts`, схема для drizzle-kit), не импортируют `server-only`: в обычном Node он выбрасывает ошибку.
6. **Доступ к данным:** к БД обращается только `server/`. Фронтенд получает данные через публичный API серверных модулей (`@server/issues` и т. п.), напрямую `@server/db` из фронтенда (`src/`, `app/`) импортировать нельзя (ESLint). Это замена прежнего слоя `lib/dal`.
7. **Направление зависимостей:** UI → `server`, но никогда наоборот: `server/` не импортирует ничего из `src/` и `app/` (ESLint запрещает алиас `@/*` внутри `server/`).
8. **Server Actions** лежат в `features/*/api/*.actions.ts` (`"use server"`) и вызывают модули `server`. В гайде FSD они не описаны, это наше соглашение.
9. **Не мусор:** одна ответственность на файл, без «utils.ts на всё», именованные экспорты, никаких циклических импортов (проверяет линтер, см. задачу 1.0).

## Правила проекта

- Запросы к БД идут только через модули `server/`, см. архитектуру выше.
- Каждое решение о кэше записываем в `docs/adr/`: что, почему, чем рискуем.
- На каждом этапе сначала делаем «наивно», потом ломаем (гонки, медленная сеть, искусственные задержки) и только потом чиним.

## Задача 1.2. Схема БД на Drizzle

**Сделать**
- Файл `drizzle.config.ts`.
- Схема в `db/schema/`, по файлу на группу таблиц, не один большой файл:
  - `workspaces`, `projects`, `issues`, `comments`, `labels`, `issue_labels` (many-to-many), `workspace_members` (с ролью).
  - У `issues`: `number` (порядковый номер внутри workspace, как `TRK-42`), `title`, `description`, `status` (enum), `priority` (enum), `assigneeId` (nullable), `createdAt`, `updatedAt`.
  - У `workspaces`: `slug` (нужен для маршрутов).
- Таблицы пользователей и сессий Better Auth добавим на этапе 2. Сейчас `assigneeId` и подобные поля оставь обычным `text`/`uuid` без внешнего ключа на пользователей.
- Скрипты `db:generate`, `db:migrate`.

**Приёмка**
- [ ] `npm run db:generate` создаёт SQL-миграцию, `npm run db:migrate` применяет её.
- [ ] Есть внешние ключи с осмысленным `onDelete`: удаление проекта не оставляет задачи-сироты, удаление label не удаляет задачи.
- [ ] Есть индексы под будущие запросы: список задач workspace по статусу, по исполнителю, по дате.
- [ ] `(workspaceId, number)` уникальны.

**Подумать и объяснить:** почему `number` нельзя просто сделать `serial`? (Он должен быть последовательным в рамках каждого workspace.)

## Задача 1.4. Каркас приложения (по FSD)
