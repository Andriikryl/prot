# Tracker (мини-Linear): план и задачи

Формат работы: задачу делает разработчик, Claude проверяет (код, сборка, запуск) и даёт замечания по пунктам. Готовых решений не даём, только направление и ссылки на доки.

Сдача: напиши «готово 1.х», и я проверю.

Доки Next 16 лежат в `node_modules/next/dist/docs/01-app/`. Читать перед работой: API отличаются от старых версий.

## Стек

Next.js 16.4, React 19.3, Postgres 17 (Docker), Drizzle, Better Auth, zod, Tailwind 4, shadcn/ui (radix-nova, компоненты в `components/ui`), nuqs, dnd-kit, TanStack Virtual, Vitest, Playwright.

## Сущности

User, Workspace, Project, Issue (статус, приоритет, исполнитель, метки), Comment, ActivityLog.

## Структура маршрутов (цель)

```
app/
  (auth)/login, register
  (app)/
    [workspace]/
      layout.tsx            # сайдбар, проверка членства
      issues/page.tsx       # список + фильтры из URL
      issues/[id]/page.tsx  # полная страница задачи
      @modal/(.)issues/[id] # перехваченная модалка (intercepting + parallel)
      projects/[id]/
      settings/
  api/events/route.ts       # SSE для realtime
```

## Архитектура: стартовый Next + отдельный бэкенд `server/`

Решение: фронтенд на стандартной структуре Next (без FSD, она давала слишком много церемоний для проекта такого размера), бэкенд отдельно в `server/`.

### Раскладка папок

```
app/                      # страницы, layouts, route handlers. Реальный код, не реэкспорты
components/
  ui/                     # shadcn/ui
hooks/                    # хуки (use-mobile)
lib/                      # утилиты (cn)
proxy.ts                  # (позже) в корне, рядом с app/
server/                   # БЭКЕНД (алиас @server/*). Не знает про React и UI
  db/                     # схема, миграции, клиент (client.ts), сид; вход для приложения: index.ts (server-only)
  workspaces/ issues/     # модули: queries.ts + публичный index.ts (server-only)
  auth/                   # (этап 2) сессии, проверка прав
```

Алиасы: `@/*` указывает на корень проекта (фронтенд), `@server/*` на `server/`.

### Правила

1. **Страницы и layouts живут в `app/`.** Повторно используемые компоненты в `components/`. Выносим из страницы только когда появляется второе использование, не дробим заранее.
2. **Server/client:** публичный вход каждого модуля `server/*` начинается с `import "server-only"`, поэтому клиентский компонент, который его импортирует, ломает сборку. Исключение: файлы, которые запускаются вне Next (`db/client.ts`, `db/seed.ts`, схема для drizzle-kit), не импортируют `server-only`: в обычном Node он выбрасывает ошибку.
3. **Доступ к данным:** к БД обращается только `server/`. Фронтенд получает данные через публичный API серверных модулей (`@server/issues` и т. п.), напрямую `@server/db` из фронтенда импортировать нельзя (ESLint).
4. **Направление зависимостей:** UI → `server`, но никогда наоборот: `server/` не импортирует фронтенд (ESLint запрещает алиас `@/*` внутри `server/`).
5. **Server Actions** лежат в `actions.ts` рядом с маршрутом в `app/` (`"use server"`) и вызывают модули `server`.
6. **Не мусор:** одна ответственность на файл, без «utils.ts на всё», именованные экспорты, никаких циклических импортов.
7. **Проверка:** `npm run check` (typecheck + ESLint).

## Правила проекта

- Запросы к БД идут только через модули `server/`, см. архитектуру выше.
- Каждое решение о кэше записываем в `docs/adr/`: что, почему, чем рискуем.
- На каждом этапе сначала делаем «наивно», потом ломаем (гонки, медленная сеть, искусственные задержки) и только потом чиним.

## Задача 1.2. Схема БД на Drizzle

**Сделать**
- Файл `drizzle.config.ts`.
- Схема в `server/db/schema/`, по файлу на группу таблиц, не один большой файл:
  - `workspaces`, `projects`, `issues`, `comments`, `labels`, `issue_labels` (many-to-many), `workspace_members` (с ролью).
  - У `issues`: `number` (порядковый номер внутри workspace, как `TRK-42`), `title`, `description`, `status` (enum), `priority` (enum), `assigneeId` (nullable), `createdAt`, `updatedAt`.
  - У `workspaces`: `slug` (нужен для маршрутов).
- Таблицы пользователей и сессий Better Auth добавим на этапе 2. Сейчас `assigneeId` и подобные поля оставь обычным `text`/`uuid` без внешнего ключа на пользователей.
- Скрипты `db:generate`, `db:migrate`.

**Приёмка**
- [ ] `npm run db:generate` создаёт SQL-миграцию, `npm run db:migrate` применяет её.
- [ ] Есть внешние ключи с осмысленным `onDelete`: удаление проекта не оставляет задачи-сироты, удаление label не удаляет задачи.
- [ ] Есть индексы под будущие запросы: список задач workspace по статусу, по исполнителю, по дате.
- [ ] `(workspaceId, number)` уникальны.

**Подумать и объяснить:** почему `number` нельзя просто сделать `serial`? (Он должен быть последовательным в рамках каждого workspace.)
